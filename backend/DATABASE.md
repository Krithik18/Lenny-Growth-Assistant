# Database implementation

Status: database code is implemented, but no Supabase project is configured and no hosted
tables have been created. Offline checks cannot confirm that a live migration succeeds.

## Structure

All 11 application tables live in the `app_data` schema. Supabase owns `auth.users`;
the migration references it but never creates or removes it.

| Model file | Tables |
| --- | --- |
| `app/db/models/chat.py` | profiles, conversations, messages, generations |
| `app/db/models/knowledge.py` | episodes, episode_revisions, transcript_chunks, message_sources, ingestion_runs |
| `app/db/models/artifacts.py` | artifacts, artifact_versions |

`app/db/base.py` defines the shared metadata, UUID identifiers, timestamps, and constraint
naming. IDs are generated by Python on insert; profiles instead use an existing Supabase
user ID. `updated_at` is advanced by SQLAlchemy updates; raw SQL writers must update it explicitly.

Constraints enforce valid states, positive sequence/version values, citation uniqueness,
and foreign-key references. An episode's active revision must belong to that episode.
Referenced transcript revisions/chunks cannot be deleted while citations depend on them.
Deleting a conversation cascades to its messages and artifacts.

Vector columns initially have variable dimensions because an embedding model has not been
selected. Embedding model and dimension metadata must accompany each non-null vector.
The future retrieval service must filter by compatible model/dimensions and active revisions.
A later migration will add a fixed-dimension or model-specific vector index after that choice.
There is no vector search query or ingestion implementation yet.

## Configure Supabase later

1. Create a Supabase project.
2. Copy its PostgreSQL **direct connection or session pooler** URL from Connect.
   A session pooler is useful if the development network cannot reach the direct IPv6 host.
   Do not use the HTTPS project URL or the transaction-pooler URL for this implementation.
3. Copy `.env.example` to `.env` if it does not exist, and set `DATABASE_URL` there.
   URL-encode special characters in the database password. Use `?sslmode=require` for
   the hosted connection (the adapter translates it for asyncpg). Never commit the real URL.
4. From `backend`, run:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
```

The migration requires a database role allowed to create schemas, enable pgvector, create
tables, and reference `auth.users` (the Supabase PostgreSQL administrative connection can
perform these setup operations). Plain PostgreSQL without Supabase Auth is not a supported
target for this initial migration.

The API never creates tables on startup. Restart it after configuring `.env`, then visit
`/health/ready`. A successful readiness check confirms connectivity and migration version;
it does not exhaustively validate every table or model provider.

## File and execution flow

```text
.env → config.py → main.py lifespan → Database in db/session.py
                                      ├─ connection pool
                                      └─ async session factory

Future route → Depends(get_session) → service reads/writes → explicit commit
                                      └─ request cleanup rolls back leftovers and closes session

alembic upgrade head → migrations/env.py → DATABASE_URL
                     → versions/0001_initial.py
                     → app_data tables + constraints + RLS
                     → app_data.alembic_version
```

One async session is used per request; do not share it between concurrent tasks. Service
code must explicitly commit successful writes before returning. Exceptions or uncommitted
work are rolled back at cleanup. Avoid holding a transaction during a long model request.
Shutdown disposes the connection pool.

## Access boundaries

The schema is kept outside the default public Data API schema. The migration enables RLS
and revokes schema/table access from PUBLIC, anon, and authenticated. No client-facing RLS
policies are installed, and no private CRUD endpoints are exposed yet. Browser clients
must access private records through future authenticated FastAPI endpoints.

RLS does not isolate users when the backend uses an owner/BYPASSRLS role. Token validation,
conversation ownership checks, same-conversation validation for generation/artifact links,
and request deduplication before message creation must be implemented in the service layer
before exposing those operations. The current generation request constraint is scoped to
an existing user message, not to an entire HTTP request across new messages.

## Migration maintenance and checks

The initial migration contains frozen SQL; it never imports live ORM models. Future model
changes need a new reviewed migration. Autogeneration is limited to `app_data`, and the
external auth FK is excluded from automatic management. Alembic autogeneration does not
fully manage RLS, extension setup, or all check-constraint changes; review these manually.
Update `app/db/schema_version.py` when adding a new migration head.

```powershell
# Generate SQL for review without connecting to a database.
.\.venv\Scripts\python.exe -m alembic upgrade head --sql

# After configuring the database, check for differences from ORM metadata.
.\.venv\Scripts\python.exe -m alembic check

.\.venv\Scripts\python.exe -m pytest -q
```

Downgrading the initial migration deletes application data. It leaves Supabase auth users,
the vector extension, and the app_data schema intact. Do not downgrade a populated project
unless data loss is explicitly intended and recoverable.
